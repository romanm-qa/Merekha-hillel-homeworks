# Lesson 31. Jenkins — вопросы и ответы

## 1. Что такое Jenkins?

Jenkins — сервер автоматизации с открытым исходным кодом, который используется для построения CI/CD-процессов: получения кода, сборки, тестирования, публикации результатов и развёртывания приложения.

## 2. Что такое CI?

Continuous Integration — практика регулярного объединения изменений в общем репозитории с автоматическим запуском проверок. Она помогает обнаруживать проблемы вскоре после изменения кода.

## 3. В чём разница между Continuous Delivery и Continuous Deployment?

При Continuous Delivery проверенная версия готова к production, но релиз подтверждает человек. При Continuous Deployment успешная версия автоматически разворачивается в production.

## 4. Что такое Jenkins Pipeline?

Pipeline — последовательность автоматизированных этапов, например `Checkout → Build → Test → Deploy`.

## 5. Что такое Pipeline as Code?

Это подход, при котором pipeline описывается кодом и хранится в репозитории. В Jenkins обычно используется файл `Jenkinsfile`.

## 6. Какие преимущества даёт `Jenkinsfile` в репозитории?

- версионирование pipeline;
- история изменений;
- code review;
- воспроизводимость;
- хранение конфигурации рядом с кодом проекта.

## 7. В чём разница между Declarative и Scripted Pipeline?

Declarative Pipeline использует строгую стандартную структуру и проще поддерживается. Scripted Pipeline является более свободным Groovy-скриптом, даёт больше контроля, но обычно сложнее читается.

## 8. Что такое stage и step?

Stage — логический этап pipeline, например `Test`. Step — конкретное действие внутри стадии, например запуск команды `pytest`.

## 9. Что означает `agent any`?

Pipeline может выполняться на любом доступном Jenkins-agent.

## 10. Что такое Jenkins agent?

Agent — машина или окружение, где фактически выполняются команды pipeline. Controller управляет Jenkins и распределяет задачи между агентами.

## 11. Что такое Jenkins job и build?

Job — настроенная задача Jenkins. Build — один конкретный запуск этой задачи.

## 12. Что такое Jenkins workspace?

Workspace — рабочая директория build, куда Jenkins получает код и где выполняет команды.

## 13. Как Jenkins получает код из Git?

Через шаги `git` или `checkout scm`. При `Pipeline script from SCM` параметры репозитория и ветки берутся из конфигурации job.

## 14. Чем `checkout scm` отличается от `git`?

`checkout scm` использует SCM-конфигурацию текущей job. Шаг `git` получает явно заданный URL и ветку.

## 15. Для чего нужен блок `post`?

Для действий после выполнения основных стадий: публикации результатов, сохранения артефактов, очистки окружения и уведомлений.

## 16. Почему результаты тестов публикуют в `post { always { ... } }`?

Чтобы Jenkins попытался сохранить отчёт даже тогда, когда тесты упали и стадия завершилась ошибкой.

## 17. Как Jenkins понимает, что команда завершилась ошибкой?

По exit code. Код `0` обычно означает успех, ненулевой код — ошибку.

## 18. Что такое JUnit XML?

Стандартный XML-формат результатов тестирования. Jenkins читает его и показывает количество passed, failed и skipped-тестов, длительность и историю запусков.

## 19. Может ли pytest создавать JUnit XML?

Да:

```bash
pytest --junitxml=test-reports/results.xml
```

## 20. Создаёт ли Jenkins-шаг `junit` результаты тестов?

Нет. Он только читает и публикует уже созданные XML-файлы.

## 21. Как связаны `allure-pytest` и Allure Jenkins Plugin?

`allure-pytest` создаёт сырые результаты в `allure-results`. Jenkins Plugin с помощью Allure Commandline генерирует и публикует отчёт в Jenkins.

## 22. Можно ли использовать JUnit и Allure одновременно?

Да. JUnit удобен для встроенной статистики Jenkins, Allure — для подробного отчёта с шагами и attachments.

## 23. Для чего Jenkins Credentials?

Для безопасного хранения токенов, паролей, SSH-ключей и других секретов. В pipeline используют ID credentials, а не записывают секрет в код.

## 24. Нужны ли credentials для публичного GitHub-репозитория?

Для чтения публичного репозитория обычно нет. Для приватного репозитория требуется авторизация.

## 25. Почему `source .venv/bin/activate` в отдельном `sh` может не сработать?

Потому что следующий `sh` может выполняться в новой оболочке, где окружение уже не активировано. Надёжнее вызывать `.venv/bin/python` и `.venv/bin/pip` напрямую.

## 26. Зачем использовать Docker вместе с Jenkins?

Jenkins отвечает за запуск и последовательность этапов, а Docker предоставляет одинаковое изолированное окружение с нужными версиями программ и зависимостей.

## 27. Обязателен ли Docker для Jenkins?

Нет. Jenkins может запускать команды прямо на агенте. Docker используется, если проекту требуется воспроизводимое контейнерное окружение.

## 28. Как передать Jenkins результат тестов из Docker Compose?

Compose должен вернуть exit code контейнера с тестами, например:

```bash
docker compose up --abort-on-container-exit --exit-code-from tests
```

## 29. Зачем очищать Docker-окружение после pipeline?

Чтобы остановленные контейнеры, сети и тестовые данные не влияли на следующий запуск и не занимали ресурсы.

## 30. Что такое artifact в Jenkins?

Файл, сохранённый после build: лог, скриншот, видео, архив, HTML-отчёт или собранный пакет.

## 31. Какими способами можно запустить pipeline?

Вручную, webhook, Poll SCM, расписанием, через API или после другой job.

## 32. Почему GitHub не может отправить webhook на локальный Jenkins?

Адрес `localhost` доступен только на компьютере пользователя и не маршрутизируется из интернета. Нужен публично доступный Jenkins или туннель.

## 33. Чем webhook отличается от Poll SCM?

При webhook GitHub сразу сообщает Jenkins о событии. При Poll SCM Jenkins периодически самостоятельно проверяет репозиторий.

## 34. В чём разница между staging и production?

Staging — проверочное окружение перед релизом с тестовыми данными. Production — рабочее окружение реальных пользователей и реальных данных.

## 35. Как Jenkins может участвовать в деплое?

После успешной сборки и тестов Jenkins может опубликовать Docker-образ, развернуть его на staging, запустить staging-тесты и затем выполнить или разрешить production-деплой.

## 36. Почему желательно продвигать один Docker-образ от staging к production?

Чтобы в production попала именно та сборка, которая была проверена на staging. Если образ пересобрать, его содержимое потенциально может отличаться.

## 37. Какие причины падения pipeline должен проверить автоматизатор?

- баг приложения;
- проблема автотеста;
- изменение требований;
- нестабильность теста;
- некорректные тестовые данные;
- ошибка окружения, сети или инфраструктуры.

## 38. Какие плагины нужны для нашего учебного pipeline?

Основные: Pipeline, Git, Credentials, JUnit и Allure. Остальные устанавливаются только при необходимости.

## 39. Что будет в нашем учебном pipeline?

Получение кода, сборка Docker-окружения, запуск PostgreSQL и pytest, создание JUnit XML и Allure results, публикация отчётов и очистка контейнеров.

## 40. Какая короткая формулировка лучше всего объясняет нашу схему?

Jenkins определяет, что и когда запускать; Docker предоставляет окружение; pytest выполняет тесты; JUnit и Allure показывают результаты.
