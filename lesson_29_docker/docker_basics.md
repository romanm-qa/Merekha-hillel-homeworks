## Lesson 29: Docker

### Зачем нужен Docker
Docker решает проблему "у меня работает, а у тебя нет" — когда приложение ведёт себя по-разному из-за разных версий языка, библиотек или настроек окружения на разных машинах.

Docker позволяет упаковать приложение вместе со всем необходимым (код, зависимости, конфигурация) в **контейнер** — изолированную среду, которая работает одинаково на любой машине: у разработчика, у QA, на CI-сервере, в проде.

---

### Образ (Image) vs Контейнер (Container)

- **Образ** — шаблон/рецепт приложения со всеми зависимостями. Сам по себе не выполняется, просто хранится.
- **Контейнер** — запущенный экземпляр образа. Из одного образа можно запустить сколько угодно контейнеров.

*Аналогия из Python:* образ — это класс, контейнер — это `object = MyClass()`, то есть экземпляр этого класса.

Отличие контейнера от виртуальной машины: контейнеры используют общее ядро операционной системы хоста, поэтому они значительно легче и быстрее виртуальных машин.

---

### Установка и проверка

Docker устанавливается через Docker Desktop (Windows/macOS) или через официальный скрипт (Linux).

Проверить, что Docker установлен и работает:
```bash
docker --version
docker info
```

### Dockerfile — рецепт для сборки образа

**Dockerfile** — текстовый файл с инструкциями, по которым Docker собирает образ.

Основные инструкции:

| Инструкция | Что делает |
|---|---|
| `FROM` | какой базовый образ взять за основу (например, `python:3.9`) |
| `WORKDIR` | задаёт рабочую папку внутри контейнера |
| `COPY` | копирует файлы с компьютера внутрь контейнера |
| `RUN` | выполняет команду во время сборки образа (например, установка зависимостей) |
| `CMD` | команда, которая выполнится при запуске контейнера |

Пример Dockerfile для тестирования Python-приложения:

```dockerfile
FROM python:3.9

WORKDIR /app

COPY . /app

RUN pip install pytest psycopg2

CMD ["pytest"]
```

*Простыми словами:* `FROM` — берём заготовку с Python, `WORKDIR` — говорим "дальше работаем в папке /app", `COPY` — переносим свой код внутрь, `RUN` — ставим зависимости, `CMD` — что запустится, когда контейнер стартует.

---

### Основные команды Docker CLI

| Команда | Что делает |
|---|---|
| `docker build -t myimage .` | собрать образ из Dockerfile (точка — искать Dockerfile в текущей папке) |
| `docker run myimage` | запустить контейнер из образа |
| `docker ps` | посмотреть список запущенных контейнеров |
| `docker exec -it <id> bash` | зайти "внутрь" работающего контейнера, как по SSH |
| `docker stop <id>` | остановить контейнер |
| `docker rm <id>` | удалить контейнер |
| `docker images` | список всех образов на компьютере |
| `docker rmi <образ>` | удалить образ |
| `docker pull postgres` | скачать готовый образ с Docker Hub (например, Postgres) |

### Docker Compose — управление несколькими контейнерами сразу

Когда приложению нужно несколько сервисов одновременно (например, само приложение + база данных), их описывают в одном файле `docker-compose.yml`, и запускают одной командой.

```yaml
version: '3'

services:
  db:
    image: postgres
    environment:
      POSTGRES_USER: test_user
      POSTGRES_PASSWORD: test_password
      POSTGRES_DB: test_db
    ports:
      - "5432:5432"

  app:
    build: .
    depends_on:
      - db
```

Разбор:
- **`db`** — сервис с базой данных. Используется готовый образ (`image: postgres`) — свой Dockerfile для БД писать не нужно.
- **`app`** — сервис с приложением. `build: .` означает "не бери готовый образ, а собери его сам из Dockerfile, который лежит в этой же папке".
- **`depends_on`** — говорит Docker: "сначала подними `db`, и только потом `app`" (чтобы приложение не пыталось подключиться к ещё не готовой базе).

Запуск всех сервисов сразу:
```bash
docker compose up -d
```
(`-d` — запустить в фоне, не занимая терминал)

### ⚠️ Важный нюанс: `localhost` vs имя сервиса

Это самый частый источник ошибок у новичков с Docker + БД.

- Когда ты подключаешься к Postgres **со своего компьютера** (хоста) — используешь `localhost` + порт, который "проброшен" наружу (например, `localhost:5433`, если в `ports` указано `"5433:5432"`).
- Но когда **один контейнер обращается к другому контейнеру** (например, `app` к `db`) — `localhost` внутри контейнера означает "сам этот контейнер", а не соседний. Поэтому `localhost` тут не сработает.

Вместо этого используется **имя сервиса** из `docker-compose.yml` как хост — Docker сам настраивает внутреннюю сеть, где контейнеры видят друг друга по имени. И порт указывается **внутренний** (родной порт сервиса, например `5432`), а не тот, что "проброшен" наружу.

```python
# Подключение С КОМПЬЮТЕРА (хоста):
conn = psycopg2.connect(host="localhost", port="5433", ...)

# Подключение ИЗ ОДНОГО КОНТЕЙНЕРА К ДРУГОМУ (например, app → db):
conn = psycopg2.connect(host="db", port="5432", ...)
```

*Простыми словами:* находясь "снаружи" Docker — обращайся по `localhost` и внешнему порту. Находясь "внутри" Docker-сети (один контейнер к другому) — обращайся по имени сервиса и внутреннему порту.

### Тестирование с использованием Docker

Тесты можно писать как обычные функции с `assert` (pytest их подхватит без необходимости наследовать `unittest.TestCase`):

```python
import psycopg2

def test_database_connection():
    conn = psycopg2.connect(
        dbname="test_db",
        user="test_user",
        password="test_password",
        host="db",
        port="5432"
    )
    assert conn is not None

def test_data_insertion():
    conn = psycopg2.connect(
        dbname="test_db",
        user="test_user",
        password="test_password",
        host="db",
        port="5432"
    )
    cursor = conn.cursor()
    cursor.execute("INSERT INTO users (id, name) VALUES (1, 'John')")
    conn.commit()
    cursor.execute("SELECT * FROM users WHERE id=1")
    result = cursor.fetchone()
    assert result[1] == 'John'
```

Чтобы тесты запускались автоматически при старте контейнера, в Dockerfile указывается:
```dockerfile
CMD ["pytest"]
```

Тогда достаточно:
```bash
docker build -t myapp .
docker run myapp
```
— и тесты выполнятся сразу внутри изолированного окружения.

### Итог темы
Docker позволяет:
- упаковывать приложение вместе со всеми зависимостями в переносимый контейнер,
- поднимать тестовое окружение (например, базу данных) одной командой без ручной установки,
- изолировать тесты от "грязного" локального окружения,
- через Docker Compose — запускать несколько связанных сервисов (приложение + БД) одновременно,
- автоматизировать прогон тестов внутри CI/CD-конвейера.

Ключевое правило, которое проще всего забыть: **внутри Docker-сети контейнеры общаются по имени сервиса и внутреннему порту, а не через `localhost`.**
