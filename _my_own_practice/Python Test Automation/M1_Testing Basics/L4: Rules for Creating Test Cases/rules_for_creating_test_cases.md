# L4: Правила создания тест-кейсов

## Зачем нужны правила создания тест-кейсов

Хороший тест-кейс должен соответствовать определённым стандартам.

Недостаточно просто прочитать требование и записать несколько действий для его проверки. Без общей структуры тест-кейсы становятся непонятными, неполными и сложными для повторного использования.

Основные проблемы тест-кейсов, созданных без правил:

- отсутствие структуры;
- отсутствие шагов или ожидаемых результатов;
- отсутствие понятных предусловий;
- отсутствие полноценных тестовых сценариев.

Главная причина создавать качественные тест-кейсы заключается в том, что их проще автоматизировать.

Правильно составленный тест-кейс также:

- понятен другим участникам команды;
- может выполняться разными тестировщиками одинаково;
- снижает вероятность ошибок;
- подходит для повторного использования;
- упрощает сбор статистики;
- позволяет отслеживать покрытие требований;
- может быть включён в тестовый набор или тестовый сценарий.

---

## Структура хорошего тест-кейса

Хороший тест-кейс должен содержать:

1. идентификатор тест-кейса;
2. понятное и корректное название;
3. ссылку на требование;
4. предусловия;
5. последовательные шаги;
6. ожидаемый результат для каждого шага.

Конкретная структура может немного отличаться в зависимости от особенностей проекта.

---

## 1. Идентификатор тест-кейса — Test Case ID

Каждый тест-кейс должен иметь уникальный идентификатор или номер.

Например:

`TC-5478`

Идентификатор помогает:

- быстро найти нужный тест-кейс;
- передать ссылку на него другому участнику команды;
- добавить тест-кейс в тестовый набор;
- связать его с тестовым сценарием;
- собирать статистику и метрики;
- однозначно отличать его от других тест-кейсов.

---

## 2. Понятное и корректное название

Название должно сразу объяснять, что именно проверяет тест-кейс.

Плохой пример:

> Проверка обновления.

Такое название может относиться к большому количеству разных проверок. По нему невозможно понять, какая система или функциональность тестируется.

Хороший пример:

> Проверка интерактивного обновления программы XY.

Название должно быть:

- кратким;
- конкретным;
- понятным;
- однозначным;
- связанным с проверяемой функциональностью.

Хорошее название помогает быстро найти подходящий тест-кейс, тестовый набор или тестовый сценарий.

---

## 3. Связь с требованиями

Тест-кейс должен содержать ссылку на требование, которое он проверяет.

Например:

`REQ-346 — программа XY поддерживает интерактивное обновление`

Это позволяет:

- отслеживать покрытие требований тестами;
- собирать статистику;
- понимать назначение тест-кейса;
- находить требования без тестового покрытия;
- поддерживать трассировку между требованиями и тест-кейсами.

Каждое требование должно быть покрыто как минимум одним тест-кейсом.

---

## 4. Предусловия — Preconditions

Предусловия описывают состояние системы и действия, которые необходимо выполнить перед началом основных шагов тест-кейса.

Предусловия нужны, если перед выполнением теста необходимо:

- подготовить определённое окружение;
- ознакомиться с дополнительными требованиями или документацией;
- создать необходимые тестовые данные;
- авторизоваться под определённым пользователем;
- проверить или изменить настройки;
- убедиться, что необходимый процесс или сервис запущен.

Предусловия должны быть максимально точными.

Плохой пример:

> Проверить конфигурацию.

Из такого предусловия непонятно:

- какую именно конфигурацию проверять;
- где её найти;
- какие значения должны быть установлены;
- каким способом выполнить проверку.

Хороший пример:

> Убедиться, что все репозитории работают, выполнив команду `yum repolist all`.

---

## 5. Шаги — Steps

Каждый шаг должен быть:

- понятным;
- корректным;
- последовательным;
- не слишком сложным;
- однозначным;
- доступным для повторного выполнения.

У шага должен быть только один понятный способ выполнения. Если действие можно интерпретировать по-разному, его необходимо переформулировать или разделить на несколько шагов.

Плохой пример:

> Проверить программу.

Хороший пример:

> Проверить, что процесс XY запущен, выполнив команду `service XY status`.

Использование конкретных команд и примеров снижает вероятность ошибки при выполнении тест-кейса.

Тест-кейс также можно повторно использовать в составе другого тестового набора, например для проверки той же функциональности через приложение или веб-интерфейс.

---

## 6. Ожидаемый результат для каждого шага

Для каждого шага необходимо указать ожидаемый результат.

Ожидаемый результат должен описывать:

- какое состояние системы ожидается;
- какие данные должны отображаться;
- какое сообщение должен увидеть пользователь;
- какое значение должно вернуться;
- какие изменения должны произойти;
- какие записи должны появиться в логах.

В некоторых случаях для проверки корректной работы необходимо дополнительно проверить логи системы.

Ожидаемый результат разрешается не описывать только тогда, когда он полностью очевиден. В таком случае напротив шага ставится прочерк:

`—`

## Пример хорошего тест-кейса

### Основная информация

**ID:** `TC-5478`

**Название:** Проверка интерактивного обновления программы XY

**Требование:** `REQ-346 — программа XY поддерживает интерактивное обновление`

### Предусловие

Убедиться, что все репозитории работают:

```bash
yum repolist all
```

### Шаг 1

Проверить текущую версию программы XY:

```bash
rpm -qi XY
```

**Ожидаемый результат:**

В выводе отображается информация о текущей версии программы:

```text
Name: XY
Version: 4.16.1.3
Release: 12
```

### Шаг 2

Убедиться, что процесс XY запущен:

```bash
service XY status
```

**Ожидаемый результат:**

В выводе отображается активное состояние процесса:

```text
Active: active (running)
```

Если процесс не запущен, необходимо запустить его:

```bash
service XY start
```

После этого следует повторно проверить статус процесса.

### Шаг 3

Обновить программу XY:

```bash
yum update XY
```

**Ожидаемый результат:**

- программа успешно обновлена;
- в результате отсутствуют ошибки и предупреждения;
- вывод командной строки заканчивается сообщением:

```text
Complete
```

### Шаг 4

Убедиться, что после обновления процесс XY продолжает работать:

```bash
service XY status
```

**Ожидаемый результат:**

В выводе отображается:

```text
Active: active (running)
```

### Шаг 5

Проверить версию программы после обновления:

```bash
rpm -qi XY
```

**Ожидаемый результат:**

В выводе отображается новая версия программы:

```text
Name: XY
Version: 4.25.1.3
Release: 12
```

---

## Итоги урока

Качественный тест-кейс должен быть понятным, структурированным и воспроизводимым.

Он должен содержать:

- уникальный идентификатор;
- конкретное название;
- связь с требованием;
- точные предусловия;
- понятные последовательные шаги;
- ожидаемый результат для каждого шага.

Соблюдение этих правил помогает другим тестировщикам правильно выполнять проверки, снижает вероятность ошибок и упрощает последующую автоматизацию.
