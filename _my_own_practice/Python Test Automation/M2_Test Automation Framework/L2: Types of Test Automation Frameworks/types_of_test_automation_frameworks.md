# L2: Типы фреймворков автоматизации тестирования

## Введение

Фреймворки автоматизации тестирования значительно развивались с течением времени.

Каждый подход имеет:

- определённую структуру;
- своё назначение;
- преимущества;
- недостатки;
- подходящие сценарии использования.

В уроке рассматриваются четыре основных типа:

1. линейный фреймворк;
2. модульный фреймворк;
3. фреймворк, управляемый данными;
4. фреймворк, управляемый ключевыми словами.

---

# 1. Линейный фреймворк автоматизации

## Определение

Линейный фреймворк — Linear Automation Framework — основан на принципе последовательной записи и воспроизведения действий — Record and Playback.

Тестировщик:

1. выбирает конкретную функциональность приложения;
2. записывает последовательность действий;
3. получает готовый тестовый скрипт;
4. запускает скрипт отдельно от других тестов;
5. повторяет выполнение при необходимости.

Все действия выполняются последовательно:

`Test Script 1 → Test Script 2 → Test Script 3 → Test Script N`

Сценарий может содержать:

- переходы между страницами;
- нажатия кнопок;
- заполнение полей;
- выбор элементов;
- другие пользовательские действия.

---

## Преимущества линейного фреймворка

- Не требует глубоких знаний автоматизации.
- Может не требовать написания собственного кода.
- Тестовый процесс легко понять благодаря последовательному расположению шагов.
- Тестовые скрипты можно создавать очень быстро.
- Подход удобен для начала работы с новым инструментом.
- Большинство инструментов автоматизации поддерживает запись и воспроизведение.
- Не требует сложного предварительного планирования.

---

## Недостатки линейного фреймворка

- Тестовые скрипты практически нельзя повторно использовать.
- Тестовые данные обычно жёстко записаны непосредственно в скрипте.
- Один тест нельзя легко запустить с несколькими наборами данных.
- При изменении данных необходимо редактировать сам скрипт.
- Изменения в приложении требуют значительной переработки тестов.
- Фреймворк сложно сопровождать.
- Подход плохо масштабируется при увеличении количества тестов.

---

## Когда подходит линейный фреймворк

Линейный подход может использоваться:

- для небольших проектов;
- для простых и стабильных сценариев;
- для прототипов;
- для быстрого создания демонстрационных тестов;
- при первом знакомстве с инструментом автоматизации.

Для крупных и долгосрочных проектов он обычно не подходит.

---

# 2. Модульный фреймворк

## Определение

Модульный фреймворк — Module-Based Testing Framework — предполагает разделение тестируемого приложения на отдельные:

- функции;
- разделы;
- компоненты;
- модули;
- независимые части.

Каждый модуль тестируется отдельно.

Для каждой части приложения создаётся собственный тестовый скрипт. Затем эти скрипты объединяются для построения более крупных тестовых сценариев.

Например:

- модуль авторизации;
- модуль профиля;
- модуль корзины;
- модуль оплаты;
- модуль отчётности.

---

## Абстрактный слой

Основная стратегия модульного фреймворка заключается в создании слоя абстракции.

Благодаря этому изменения в одном модуле не должны влиять на остальные части фреймворка.

Например, если изменилась форма авторизации, необходимо обновить только:

- модуль авторизации;
- связанные с ним тестовые скрипты.

Остальные тесты могут продолжить работу без изменений.

Page Object Model, который мы использовали в Playwright, является примером применения похожего модульного подхода: логика страницы хранится отдельно от тестовых сценариев.

---

## Преимущества модульного фреймворка

- Изменения в приложении затрагивают только соответствующий модуль.
- Остальные части фреймворка можно оставить без изменений.
- Тестовые скрипты отдельных модулей можно повторно использовать.
- Создание новых тест-кейсов становится проще.
- Модули можно комбинировать в разных сценариях.
- Код становится более организованным.
- Сопровождение проекта упрощается по сравнению с линейным подходом.

---

## Недостатки модульного фреймворка

- Тестовые данные всё ещё могут быть захардкожены в скриптах.
- Разные наборы данных использовать сложнее.
- Тесты часто запускаются отдельно.
- Для настройки фреймворка необходимо знание программирования.
- Первоначальное проектирование структуры требует дополнительного времени.

---

## Когда подходит модульный фреймворк

Модульный подход подходит:

- для приложений с чётко разделёнными компонентами;
- для средних и крупных проектов;
- для проектов с повторно используемой функциональностью;
- для проектов, которые регулярно изменяются;
- для команд, которым важно повторное использование кода.

# 3. Фреймворк, управляемый данными

## Определение

Фреймворк, управляемый данными — Data-Driven Framework — разделяет:

- логику тестового скрипта;
- тестовые данные.

Тестовые данные хранятся за пределами тестового скрипта.

Один тест можно выполнять несколько раз с разными наборами входных и ожидаемых данных.

В отличие от линейного и простого модульного подходов, данные не нужно жёстко записывать непосредственно в коде теста.

---

## Источники тестовых данных

Параметры могут передаваться в тесты из внешних источников:

- Excel-таблиц;
- CSV-файлов;
- текстовых файлов;
- JSON-файлов;
- XML-файлов;
- SQL-таблиц;
- баз данных;
- API;
- конфигурационных файлов.

Общая схема:

`Наборы данных → слой источника данных → тестовый скрипт → выполнение теста`

---

## Пример

Допустим, необходимо проверить авторизацию с разными данными:

| Email | Password | Expected result |
|---|---|---|
| valid@example.com | Valid123 | Успешный вход |
| invalid@example.com | Valid123 | Ошибка авторизации |
| valid@example.com | wrong | Ошибка авторизации |
| пустое значение | Valid123 | Ошибка валидации |

Вместо четырёх отдельных тестов можно создать один параметризованный тест и выполнить его четыре раза.

В `pytest` подобный подход реализуется с помощью `@pytest.mark.parametrize`.

---

## Преимущества Data-Driven Framework

- Один тест можно запускать с несколькими наборами данных.
- Разные сценарии с данными проверяются быстрее.
- Для большого количества проверок требуется меньше скриптов.
- Можно отказаться от захардкоженных данных.
- Изменение тестового скрипта не влияет на внешние данные.
- Изменение данных не требует редактирования тестовой логики.
- За короткое время можно выполнить больше проверок.
- Положительные, отрицательные и граничные случаи удобно хранить отдельно.

---

## Недостатки Data-Driven Framework

- QA-специалист должен хорошо знать программирование.
- Необходимо уметь работать с разными форматами данных.
- Нужно разработать код для подключения к внешним источникам.
- Необходимо правильно форматировать и проверять тестовые данные.
- Первоначальная настройка может занимать много времени.
- Ошибки в данных могут привести к ошибочным результатам тестирования.
- При большом количестве файлов сопровождение данных усложняется.

---

## Когда подходит Data-Driven Framework

Подход подходит, если:

- одна функция проверяется с большим количеством данных;
- необходимо тестировать положительные и отрицательные сценарии;
- используются граничные значения;
- тесты запускаются в разных окружениях;
- данные часто изменяются;
- тестовую логику необходимо отделить от данных.

---

# 4. Фреймворк, управляемый ключевыми словами

## Определение

Фреймворк, управляемый ключевыми словами — Keyword-Driven Framework — описывает действия над приложением с помощью заранее определённых ключевых слов.

Логика тестов и тестовые данные хранятся отдельно от кода.

Каждая функция приложения представляется в таблице как последовательность инструкций.

Примеры ключевых слов:

- `open`;
- `login`;
- `clicklink`;
- `inputdata`;
- `verifycredentials`;
- `checklink`;
- `openurl`.

Для правильной работы подхода необходим общий репозиторий объектов, который связывает элементы приложения с соответствующими действиями.

---

## Принцип работы

1. Команда определяет набор доступных ключевых слов.
2. Для каждого ключевого слова реализуется соответствующее действие.
3. Объекты приложения сохраняются в общем репозитории.
4. Тестовый сценарий записывается в виде таблицы.
5. Фреймворк читает таблицу.
6. Для каждого ключевого слова запускается соответствующий код.

Схема:

`Модуль приложения → тестовый скрипт → таблица ключевых слов → действие`

---

## Пример таблицы ключевых слов

| Шаг | Описание | Ключевое слово | Объект |
|---|---|---|---|
| Step 1 | Открыть личный кабинет | `clicklink` | Login button |
| Step 2 | Ввести логин | `inputdata` | Login username |
| Step 3 | Ввести пароль | `inputdata` | Login password |
| Step 4 | Проверить учётные данные | `verifycredentials` | — |
| Step 5 | Войти в систему | `login` | Submit button |

После подготовки таблицы необходимо реализовать код, который определяет действие по ключевому слову.

Во время запуска фреймворк:

1. читает строку таблицы;
2. находит ключевое слово;
3. определяет связанный объект;
4. запускает соответствующий скрипт;
5. переходит к следующему шагу.

---

## Преимущества Keyword-Driven Framework

- Для создания тестовых сценариев требуется минимальное знание программирования.
- Один набор ключевых слов можно использовать во многих тестах.
- Код можно повторно использовать.
- Тестовые сценарии разрабатываются независимо от приложения.
- Бизнес-логика сценария становится понятнее.
- Нетехнические специалисты могут участвовать в создании тестов.
- Изменения в реализации ключевого слова применяются ко всем использующим его тестам.

---

## Недостатки Keyword-Driven Framework

- Первоначальная настройка является дорогой и сложной.
- Создание фреймворка занимает много времени.
- Необходимо заранее определить и реализовать ключевые слова.
- Требуется создать репозитории объектов и библиотеки.
- Для разработки нужен опытный специалист по автоматизации.
- При масштабировании количество ключевых слов увеличивается.
- Сопровождать таблицы ключевых слов и репозитории становится сложнее.
- Неудачно спроектированные ключевые слова могут дублировать друг друга.

---

## Когда подходит Keyword-Driven Framework

Подход подходит:

- для крупных проектов;
- для стабильных бизнес-процессов;
- для команд с участием нетехнических специалистов;
- для большого количества повторяющихся действий;
- когда сценарии должны описываться на понятном предметном языке.

Robot Framework является известным примером инструмента, поддерживающего подход, основанный на ключевых словах.

---

# Сравнение подходов

| Тип фреймворка | Основная идея | Повторное использование | Работа с данными | Сложность настройки |
|---|---|---:|---:|---:|
| Линейный | Последовательная запись действий | Низкое | Данные в коде | Низкая |
| Модульный | Разделение приложения на модули | Среднее или высокое | Часто данные в коде | Средняя |
| Data-Driven | Отделение данных от логики | Высокое | Внешние источники | Средняя или высокая |
| Keyword-Driven | Описание действий ключевыми словами | Высокое | Отдельные таблицы | Высокая |

---

# Итоги урока

Основные типы фреймворков развивались друг из друга и имеют разные преимущества и недостатки.

При выборе подхода необходимо учитывать:

- размер проекта;
- сложность приложения;
- стабильность функциональности;
- количество тестовых данных;
- квалификацию команды;
- стоимость первоначальной настройки;
- требования к сопровождению;
- необходимость масштабирования.

Не следует всегда использовать только один подход.

На реальных проектах часто применяется гибридная модель, которая сочетает:

- модульную архитектуру;
- разделение тестовой логики и данных;
- повторно используемые ключевые действия;
- общие библиотеки и репозитории объектов.

Главная задача инженера по автоматизации — выбрать или объединить подходы, наиболее подходящие для конкретного проекта и тестового окружения.
