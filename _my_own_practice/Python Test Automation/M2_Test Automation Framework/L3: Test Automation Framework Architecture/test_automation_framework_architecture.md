# Архитектура фреймворка автоматизации тестирования

## Введение

В этом уроке рассматривается распространённый архитектурный шаблон для построения фреймворка автоматизации тестирования.

Мы познакомимся с каждым уровнем архитектуры и узнаем о преимуществах такого подхода.

---

## Основные понятия

Прежде чем переходить к архитектуре фреймворка, определим два основных понятия: **компонент** и **модуль**.

### Компонент (Component)

**Компоненты** — это любые объекты Python, которые используются при реализации тестового фреймворка.

К компонентам относятся:

- функции;
- классы;
- переменные;
- другие объекты Python.

### Модуль (Module)

**Модуль** — это файл с расширением `.py`, в котором объединены компоненты, относящиеся к определённой функциональности.

Например, один модуль может содержать:

- функции для работы с API;
- классы страниц;
- тестовые данные;
- вспомогательные методы;
- настройки тестового окружения.

---

## Многоуровневая архитектура

**Многоуровневая архитектура (Layered Architecture)** — один из самых известных архитектурных шаблонов.

Она часто используется как основа архитектуры фреймворка автоматизации тестирования.

В соответствии с этим подходом модули и компоненты с похожей функциональностью распределяются по отдельным горизонтальным уровням.

Каждый уровень:

- отвечает за определённую область функциональности;
- содержит связанные между собой модули и компоненты;
- выполняет собственную роль внутри приложения;
- взаимодействует с другими уровнями через определённые интерфейсы.

Модули внутри одного уровня должны работать только с той областью функциональности, за которую отвечает этот уровень.

Условное представление многоуровневой архитектуры:

1. Уровень — связанные компоненты и модули.
2. Уровень — связанные компоненты и модули.
3. Уровень — связанные компоненты и модули.
4. Уровень — связанные компоненты и модули.

---

## Трёхуровневая архитектура

Самой известной и широко используемой архитектурой фреймворков автоматизации тестирования является **трёхуровневая архитектура**.

Решение разделяется на три логических горизонтальных уровня:

1. **Data Layer** — уровень данных.
2. **Business Layer** — уровень бизнес-логики.
3. **Core Layer** — базовый уровень.

Взаимодействие уровней:

**Data Layer → передача параметров → Business Layer**

**Core Layer → предоставление интерфейсов → Business Layer**

### Data Layer — уровень данных

Уровень данных содержит параметры и данные, необходимые для выполнения тестов.

К нему могут относиться:

- тестовые данные;
- конфигурационные файлы;
- параметры окружения;
- данные пользователей;
- ожидаемые результаты;
- данные для параметризации тестов.

Data Layer передаёт необходимые параметры на уровень бизнес-логики.

### Business Layer — уровень бизнес-логики

Уровень бизнес-логики содержит действия и сценарии, описывающие поведение пользователя или бизнес-процессы приложения.

Например:

- авторизация пользователя;
- добавление автомобиля;
- оформление заказа;
- изменение данных профиля;
- удаление созданной сущности.

Этот уровень получает:

- тестовые параметры от Data Layer;
- технические интерфейсы и инструменты от Core Layer.

### Core Layer — базовый уровень

Базовый уровень содержит основные технические компоненты фреймворка.

К нему могут относиться:

- работа с браузером;
- HTTP-клиенты;
- драйверы;
- базовые классы;
- логирование;
- обработка конфигурации;
- вспомогательные методы;
- интерфейсы для взаимодействия с приложением.

Core Layer предоставляет интерфейсы, которые используются на уровне бизнес-логики.

---

## Пример взаимодействия уровней

Предположим, необходимо протестировать авторизацию пользователя.

### Data Layer

Хранит данные пользователя:

- email;
- пароль;
- адрес тестового окружения.

### Business Layer

Описывает бизнес-действие:

1. Открыть страницу авторизации.
2. Ввести email.
3. Ввести пароль.
4. Нажать кнопку входа.
5. Проверить успешную авторизацию.

### Core Layer

Предоставляет технические возможности:

- запуск браузера;
- поиск элементов;
- заполнение полей;
- нажатие кнопок;
- ожидание загрузки страницы;
- создание логов.

Таким образом, каждый уровень отвечает только за свою часть работы.

## Преимущества трёхуровневой архитектуры

Трёхуровневая архитектура предоставляет несколько важных преимуществ для фреймворка автоматизации тестирования.

### Понятная и гибкая структура

Использование уровней позволяет организовать понятную и гибкую структуру проекта.

Становится проще определить:

- где находится необходимая функциональность;
- где нужно вносить изменения;
- к какому уровню относится определённый компонент;
- какие части фреймворка отвечают за данные, бизнес-логику и техническую реализацию.

В результате упрощается разработка и сопровождение автоматизированных тестов.

### Упрощение сопровождения

Изменения обычно необходимо вносить только в одном уровне.

Например, если изменился способ взаимодействия с браузером, изменения можно внести в Core Layer, не переписывая бизнес-сценарии и тестовые данные.

Это позволяет:

- уменьшить количество дублирующегося кода;
- избежать повторного выполнения одной и той же работы;
- упростить обновление тестов;
- быстрее исправлять ошибки.

### Снижение затрат

Понятная структура и упрощённое сопровождение помогают снизить затраты на разработку и поддержку автоматизированных тестов.

Команде требуется меньше времени на:

- поиск нужного кода;
- добавление новой функциональности;
- исправление существующих тестов;
- адаптацию тестов к изменениям приложения.

## Итоги урока

Успех автоматизации тестирования во многом зависит от архитектуры тестового фреймворка.

Для большинства приложений подходит трёхуровневая архитектура, при которой решение разделяется на три логических горизонтальных уровня:

- **Data Layer** — данные и параметры;
- **Business Layer** — бизнес-действия и тестовые сценарии;
- **Core Layer** — базовые технические компоненты и интерфейсы.

Такое разделение позволяет разработчикам и QA-инженерам сосредоточиться на своих задачах, упрощает разработку тестов и делает фреймворк более понятным, гибким и удобным в сопровождении.
