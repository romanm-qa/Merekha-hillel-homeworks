# L1: Что такое фреймворк автоматизации тестирования

## Определение

Фреймворк автоматизации тестирования — Test Automation Framework, или TAF — это набор правил и соответствующих инструментов, которые работают вместе, поддерживают автоматизированное тестирование и обеспечивают полноценную отчётность о результатах выполнения тестов.

Фреймворк объединяет методы, процессы и инструменты, которые помогают QA-специалистам эффективнее создавать, запускать и поддерживать автоматизированные тесты.

Фреймворк может включать:

- методы работы с тестовыми данными;
- стандарты написания кода;
- правила организации тестов;
- процессы сохранения результатов;
- инструменты формирования отчётов;
- репозитории объектов;
- настройки тестового окружения;
- информацию для доступа к внешним ресурсам;
- общие вспомогательные компоненты;
- механизмы запуска тестов.

---

## Как работает фреймворк

Фреймворк определяет и организует объекты, которые используются в автоматизированных тестах.

Он позволяет:

- описывать тестируемые объекты;
- повторно использовать их в разных тестовых сценариях;
- выполнять действия над объектами;
- проверять состояние объектов;
- сравнивать фактические результаты с ожидаемыми;
- сохранять результаты выполнения тестов;
- формировать отчёты.

Фреймворк можно рассматривать как среду выполнения автоматизированных тестов, основанную на наборе:

- гипотез — Hypotheses;
- концепций — Concepts;
- методов и техник — Techniques.

Вместе они поддерживают установленный процесс автоматизированного тестирования.

---

## Пример на основе Playwright и pytest

В нашем проекте с QAuto отдельными элементами фреймворка можно считать:

- `pytest` — запуск и организация тестов;
- Playwright — взаимодействие с браузером;
- Page Object Model — организация страниц и действий;
- фикстуры — подготовка тестового окружения и данных;
- `.env` — хранение настроек окружения;
- `requirements.txt` — зависимости проекта;
- папку `tests` — тестовые сценарии;
- папку `pages` — Page Object-классы;
- assertions и Playwright `expect` — проверка результатов;
- отчёты, скриншоты и видео — результаты выполнения тестов.

Таким образом, Playwright сам по себе является инструментом автоматизации, а вся организованная структура проекта вместе с правилами и дополнительными инструментами образует фреймворк автоматизации.

---

## Роль фреймворка автоматизации

TAF содержит набор правил для создания и развития автоматизированных тест-кейсов.

Основные роли фреймворка:

1. эффективное использование ресурсов;
2. обеспечение последовательности автоматизации.

---

## 1. Эффективное использование ресурсов — Effectiveness of Resources

Фреймворк помогает команде эффективнее использовать:

- время;
- деньги;
- человеческие ресурсы;
- технические инструменты;
- готовые компоненты.

Автоматизация поддерживает регулярное выполнение функциональных тестов и уменьшает время, необходимое для повторных проверок.

Благодаря повторному использованию компонентов команде не приходится каждый раз создавать одинаковую логику с нуля.

Фреймворк помогает:

- уменьшить количество повторяющегося кода;
- быстрее создавать новые тесты;
- запускать больше проверок;
- сократить продолжительность регрессионного тестирования;
- уменьшить количество рутинной ручной работы.

---

## 2. Последовательность автоматизации — Consistency of Automation

Фреймворк устанавливает единые правила разработки и выполнения автоматизированных тестов.

Это обеспечивает одинаковый подход к:

- структуре тестов;
- именованию файлов и методов;
- использованию тестовых данных;
- обработке ошибок;
- логированию;
- созданию отчётов;
- запуску тестовых наборов.

Фреймворк также помогает создавать тестовые наборы путём объединения отдельных автоматизированных тестов и подготовки их к выполнению.

Последовательный подход делает автоматизацию понятнее для всей команды и упрощает развитие проекта.

## Преимущества фреймворка автоматизации

Фреймворк автоматизации не является универсальным решением всех проблем. У него есть как преимущества, так и недостатки.

### 1. Повторное использование кода — Code Reusability

Общие компоненты можно использовать в нескольких тестах.

Например:

- методы авторизации;
- действия со страницами;
- API-клиенты;
- фикстуры;
- генераторы тестовых данных;
- проверки результатов;
- вспомогательные функции.

Если логика уже реализована в одном компоненте, её не нужно копировать в каждый тест.

Это:

- уменьшает дублирование;
- ускоряет разработку;
- упрощает поддержку;
- снижает вероятность ошибок.

### 2. Снижение затрат — Low Cost

Создание фреймворка требует первоначальных вложений, но при длительном использовании автоматизация может снизить стоимость тестирования.

Экономия достигается благодаря:

- повторному использованию кода;
- автоматическому выполнению регрессионных тестов;
- сокращению ручной работы;
- быстрому обнаружению дефектов;
- запуску тестов без постоянного участия человека.

Преимущество становится заметным на стабильных проектах с большим количеством повторяющихся проверок.

### 3. Минимальное вмешательство — Minimal Interference

После настройки автоматизированные тесты могут запускаться с минимальным участием человека.

Например, тесты могут автоматически запускаться:

- после добавления нового кода;
- при создании Pull Request;
- по расписанию;
- перед выпуском новой версии;
- в CI/CD-пайплайне.

Тестировщику не нужно вручную выполнять каждый тестовый сценарий.

### 4. Полноценная отчётность — Comprehensive Reporting

Фреймворк может автоматически собирать информацию о выполнении тестов.

Отчёт может содержать:

- количество пройденных тестов;
- количество упавших тестов;
- пропущенные тесты;
- продолжительность выполнения;
- сообщения об ошибках;
- логи;
- скриншоты;
- видеозаписи;
- трассировки;
- сведения о тестовом окружении.

Подробные отчёты помогают быстрее анализировать ошибки и принимать решения о качестве продукта.

## Недостатки фреймворка автоматизации

### 1. Зависимость от выбранного фреймворка

Скрипты, созданные для конкретного фреймворка, не всегда можно использовать в другом фреймворке без изменений.

Например, переход с Selenium на Playwright может потребовать переработки:

- локаторов;
- методов взаимодействия с браузером;
- ожиданий;
- фикстур;
- настроек запуска;
- отчётности.

### 2. Сложность сопровождения

Изменения в тестируемом приложении могут потребовать значительной переработки автоматизированных тестов.

Проблемы возникают, если:

- архитектура фреймворка плохо спроектирована;
- код сильно связан;
- компоненты нельзя повторно использовать;
- локаторы нестабильны;
- тесты зависят друг от друга;
- отсутствуют общие правила разработки.

Иногда масштабировать существующие модули бывает сложно.

### 3. Жёстко заданные тестовые данные

В некоторых проектах тестовые данные остаются захардкоженными непосредственно в тестовых скриптах.

Например:

`email = "test@example.com"`

Это усложняет:

- повторное использование тестов;
- запуск с разными наборами данных;
- поддержку разных окружений;
- параметризацию;
- параллельное выполнение.

Тестовые данные лучше отделять от тестовой логики.

### 4. Необходимость знания программирования

Для создания и сопровождения автоматизированных тестов необходимо понимать:

- язык программирования;
- функции и классы;
- объектно-ориентированное программирование;
- работу с зависимостями;
- исключения;
- структуры данных;
- архитектурные подходы;
- системы контроля версий.

Одного знания ручного тестирования для полноценной разработки TAF недостаточно.

### 5. Высокая стоимость первоначальной настройки

Первоначальное создание фреймворка может быть дорогим, сложным и длительным.

Необходимо:

- выбрать технологии;
- спроектировать архитектуру;
- настроить окружение;
- создать структуру проекта;
- подключить отчётность;
- организовать логирование;
- настроить CI/CD;
- разработать общие компоненты;
- подготовить документацию.

До появления заметной пользы команда должна потратить время на первоначальную реализацию.

### 6. Необходимость знания самого фреймворка

QA-специалисты должны понимать устройство и правила используемого фреймворка.

Нужно знать:

- структуру проекта;
- правила создания тестов;
- расположение общих компонентов;
- способы запуска тестов;
- работу фикстур;
- систему отчётности;
- процесс добавления новых сценариев.

Без этих знаний тесты могут нарушать архитектуру проекта и становиться сложными для поддержки.

## Итоги урока

Фреймворк автоматизации тестирования — это набор правил, методов, процессов и инструментов для создания и развития автоматизированных тестов.

Он может включать:

- методы работы с тестовыми данными;
- стандарты написания кода;
- механизмы сохранения результатов;
- репозитории объектов;
- способы доступа к внешним ресурсам;
- инструменты запуска и отчётности.

Основные роли TAF:

- эффективное использование ресурсов;
- обеспечение последовательности автоматизации.

Главные преимущества:

- повторное использование кода;
- снижение долгосрочных затрат;
- минимальное участие человека при запуске;
- полноценная отчётность.

Основные недостатки:

- зависимость от выбранных технологий;
- затраты на сопровождение;
- возможное использование захардкоженных данных;
- необходимость знания программирования;
- высокая стоимость первоначальной настройки;
- необходимость изучения архитектуры фреймворка.

Фреймворк не является универсальным решением. Его эффективность зависит от качества архитектуры, особенностей проекта и правильности выбранного подхода.
