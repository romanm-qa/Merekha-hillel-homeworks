# Test Reports: вопросы и ответы для собеседования

## 1. Зачем нужны отчёты о результатах автотестов?

Отчёт помогает быстро увидеть общий результат запуска, найти упавшие тесты и понять причины ошибок. В CI/CD он также служит доступным для команды артефактом: в нём можно хранить параметры, шаги, логи, скриншоты и ответы API.

## 2. Почему вывода pytest в терминале может быть недостаточно?

Терминальный вывод удобен локально, но его сложнее анализировать после CI-запуска и показывать нетехническим участникам команды. В нём также нет удобной навигации, группировки, истории и просмотра вложений.

## 3. Какие инструменты для тестовых отчётов в pytest вы знаете?

Для простого HTML-отчёта можно использовать `pytest-html`. Для более подробного интерактивного отчёта со шагами, метаданными, вложениями и историей часто используют Allure с адаптером `allure-pytest`.

## 4. Что такое `pytest-html`?

`pytest-html` — плагин pytest, создающий HTML-отчёт после выполнения тестов. В нём отображаются окружение, сводка, результаты отдельных тестов, время выполнения и сведения об ошибках.

## 5. Как установить и запустить `pytest-html`?

```bash
pip install pytest-html
pytest --html=report.html
```

После запуска будет создан HTML-отчёт.

## 6. Для чего нужен `--self-contained-html`?

Флаг встраивает необходимые стили и ресурсы в один HTML-файл:

```bash
pytest --html=report.html --self-contained-html
```

Такой отчёт удобнее передавать коллегам и сохранять как CI-артефакт.

## 7. Как настроить постоянную генерацию `pytest-html` отчёта?

Параметры можно записать в `pytest.ini`:

```ini
[pytest]
addopts = --html=report.html --self-contained-html
```

После этого отчёт будет создаваться при обычном запуске `pytest`.

## 8. Есть ли в `pytest-html` встроенная история запусков?

Полноценной встроенной истории и аналитики предыдущих запусков у `pytest-html` нет. Обычно каждый прогон создаёт новый статический отчёт, а хранение предыдущих файлов организуется средствами CI/CD.

## 9. Попадают ли скриншоты в `pytest-html` автоматически?

Нет. Скриншот нужно создать в тесте или hook и явно добавить в отчёт через extras API плагина. Само наличие файла со скриншотом не прикрепляет его к результату теста.

## 10. Можно ли изменить оформление `pytest-html`?

Да, собственный CSS можно подключить через параметр:

```bash
pytest --html=report.html --css=style.css
```

Также отчёт можно расширять через pytest hooks.

## 11. Что такое Allure?

Allure — система создания интерактивных тестовых отчётов. Она поддерживает шаги, параметры, вложения, severity, группировку по функциональности, ссылки на задачи и историю запусков.

## 12. Из каких частей состоит интеграция Allure с pytest?

`allure-pytest` собирает результаты выполнения тестов, а отдельный Allure CLI преобразует эти результаты в HTML-отчёт и открывает его. Одного Python-пакета для просмотра готового отчёта недостаточно.

## 13. Как установить поддержку Allure для pytest?

```bash
pip install allure-pytest
```

Дополнительно нужно установить Allure CLI и проверить его командой:

```bash
allure --version
```

## 14. Как собрать сырые результаты Allure?

```bash
pytest --alluredir=allure-results
```

Папка `allure-results` содержит JSON-файлы и вложения, но это ещё не готовый HTML-отчёт.

## 15. Как быстро открыть Allure-отчёт?

```bash
allure serve allure-results
```

Команда временно генерирует отчёт, запускает локальный сервер и открывает страницу в браузере.

## 16. Как сгенерировать постоянный Allure-отчёт?

```bash
allure generate allure-results -o allure-report --clean
allure open allure-report
```

`allure-results` содержит сырые результаты, а `allure-report` — сгенерированный отчёт.

## 17. Зачем используется `--clean`?

Флаг удаляет содержимое старой директории отчёта перед генерацией нового. Это предотвращает смешивание устаревших файлов с результатами текущего запуска.

## 18. В чём разница между `allure serve` и `allure generate`?

`allure serve` создаёт временный отчёт и сразу открывает его через локальный сервер. `allure generate` создаёт постоянную директорию отчёта, которую можно отдельно хранить или публиковать.

## 19. Что делают `epic`, `feature` и `story`?

Это уровни бизнес-группировки тестов:

- `epic` — крупное направление продукта;
- `feature` — конкретная функциональность;
- `story` — отдельный пользовательский сценарий внутри функциональности.

Они помогают анализировать отчёт по поведению продукта, а не только по структуре файлов.

## 20. Для чего нужны `title` и `description`?

`title` заменяет техническое имя функции понятным названием теста в отчёте. `description` объясняет цель проверки, предусловия или ожидаемое поведение.

```python
@allure.title("Успешная авторизация пользователя")
@allure.description("Проверяем вход с корректными учётными данными")
def test_login():
    ...
```

## 21. Что такое severity в Allure?

Severity обозначает критичность проверяемой функциональности. Доступны уровни `BLOCKER`, `CRITICAL`, `NORMAL`, `MINOR` и `TRIVIAL`. Severity относится к важности теста, а не к фактической серьёзности найденного дефекта.

## 22. Чем `BLOCKER` отличается от `CRITICAL`?

`BLOCKER` обычно означает, что без проверяемой функции продукт или ключевой процесс фактически невозможно использовать. `CRITICAL` относится к очень важной функции, серьёзная проблема в которой значительно влияет на пользователя, но не обязательно полностью блокирует систему.

## 23. Что такое шаги Allure?

Шаги показывают логические действия внутри теста: подготовку, выполнение действия и проверку результата. Они делают отчёт понятнее и помогают определить, на каком именно этапе произошла ошибка.

## 24. Как создать шаг через декоратор?

```python
@allure.step("Авторизуемся пользователем {email}")
def login(email, password):
    ...
```

Значения аргументов можно подставлять в название шага.

## 25. Как создать шаг без отдельной функции?

```python
with allure.step("Проверяем успешный результат"):
    assert response.status_code == 200
```

Контекстный менеджер удобен для локального логического блока внутри теста.

## 26. Нужно ли превращать каждую строку теста в Allure step?

Нет. Слишком мелкие шаги перегружают отчёт. Лучше выделять действия, значимые для понимания сценария: подготовку данных, запрос или UI-действие, а также ключевую проверку.

## 27. Что такое attachment в Allure?

Attachment — данные, прикреплённые к результату теста или шагу: текст, JSON, HTML, логи, скриншот, видео или другой файл. Вложения помогают разобраться в падении без повторного локального запуска.

## 28. Как прикрепить JSON к Allure-отчёту?

```python
allure.attach(
    response.text,
    name="API response",
    attachment_type=allure.attachment_type.JSON,
)
```

Для валидного JSON можно предварительно использовать `json.dumps(data, indent=2)`.

## 29. Как прикрепить скриншот Playwright?

```python
screenshot = page.screenshot()

allure.attach(
    screenshot,
    name="Screenshot on failure",
    attachment_type=allure.attachment_type.PNG,
)
```

Чаще всего скриншоты автоматически прикрепляют в pytest hook или fixture только при падении теста.

## 30. Чем `allure.attach()` отличается от `allure.attach.file()`?

`allure.attach()` принимает содержимое в виде строки или bytes. `allure.attach.file()` прикрепляет уже существующий файл по его пути.

## 31. Как Allure отображает параметризованные тесты?

Каждый набор параметров отображается как отдельный результат. Allure показывает значения аргументов, а динамический заголовок можно сформировать через placeholders в `@allure.title`.

## 32. Какие статусы есть в Allure?

- `Passed` — тест прошёл;
- `Failed` — проверка завершилась неуспешно;
- `Broken` — тест не выполнился корректно из-за ошибки кода или инфраструктуры;
- `Skipped` — тест пропущен;
- `Unknown` — статус не удалось корректно определить.

## 33. В чём разница между `Failed` и `Broken`?

`Failed` чаще связан с проваленной проверкой ожидаемого поведения, например `assert`. `Broken` обычно означает исключение в тестовом коде, fixture, setup или инфраструктуре. Однако итоговая классификация зависит от типа исключения и адаптера.

## 34. Что такое история запусков в Allure?

История позволяет сравнивать результаты тестов между прогонами и видеть тренды, повторные падения и стабильность. Она не возникает автоматически только из-за нескольких локальных запусков: данные `history` предыдущего отчёта нужно перенести в результаты следующего запуска или настроить это в CI.

## 35. Что такое retries в Allure?

Retries показывают несколько результатов одного теста в рамках запуска или сохранённой истории, например после повторного запуска упавшего теста. Они помогают обнаруживать flaky-тесты, но успешный retry не устраняет причину нестабильности.

## 36. Что такое flaky-тест?

Flaky-тест периодически проходит и падает без соответствующего изменения продукта. Причинами могут быть ожидания, общие тестовые данные, порядок тестов, нестабильная сеть, асинхронность или зависимость от внешнего сервиса.

## 37. Для чего нужны `issue`, `link` и `testcase`?

Они связывают результат теста с внешними ресурсами:

- `issue` — с дефектом;
- `testcase` — с тест-кейсом;
- `link` — с произвольной документацией или страницей.

Для коротких идентификаторов вроде `QA-123` шаблон URL обычно дополнительно настраивается параметрами запуска Allure.

## 38. Как Allure интегрируется с CI/CD?

CI запускает pytest со сбором `allure-results`, после чего генерирует или публикует отчёт. Jenkins может использовать Allure plugin, а в других системах сырые результаты и HTML-отчёт сохраняются как artifacts или публикуются на отдельной странице.

## 39. Какие данные нельзя бездумно добавлять в отчёт?

Нельзя прикреплять пароли, токены, cookies, персональные данные и другие секреты. Перед добавлением request/response, headers, логов или environment-информации чувствительные значения нужно маскировать.

## 40. В чём основные различия между `pytest-html` и Allure?

`pytest-html` проще установить и использовать: он сразу создаёт статический HTML-файл. Allure требует Python-адаптер и отдельный CLI, зато поддерживает шаги, бизнес-группировку, вложения, severity, ссылки и историю запусков.

## 41. Когда достаточно `pytest-html`?

Он подходит для небольшого проекта, локальной отладки или ситуации, когда нужен простой переносимый файл с базовыми результатами без сложной инфраструктуры.

## 42. Когда лучше выбрать Allure?

Allure полезен в командном проекте и CI/CD, когда требуется подробный анализ падений, шаги, вложения, бизнес-группировка, история и удобное представление результатов для разных участников команды.

## 43. Какие недостатки есть у Allure?

Он сложнее в установке и поддержке, требует отдельного CLI, занимает больше места из-за результатов и вложений, а историю нужно настраивать. Избыточные steps и attachments также могут сделать отчёт тяжёлым и неудобным.

## 44. Что вы обычно прикрепляли бы к отчёту UI-теста?

При падении я бы прикреплял скриншот, текущий URL, при необходимости trace или видео, а также короткие диагностические логи. Не стоит прикреплять большие данные ко всем успешно прошедшим тестам без практической необходимости.

## 45. Что вы обычно прикрепляли бы к отчёту API-теста?

Полезны endpoint, method, status code, sanitized request и response body, а иногда время ответа. Authorization headers, cookies и токены перед прикреплением обязательно нужно удалить или замаскировать.

## 46. Как выбрать хороший уровень детализации отчёта?

Отчёт должен позволять понять сценарий и причину падения без изучения исходного кода, но не должен дублировать каждую техническую операцию. Я бы добавлял бизнес-понятный title, несколько значимых steps и диагностические attachments преимущественно при ошибках.

## 47. Как бы вы настроили отчётность в AQA-проекте?

Локально я бы оставил быстрый запуск pytest и возможность открыть Allure через `allure serve`. В CI тесты создавали бы `allure-results`, прикрепляли диагностические данные при падениях и публиковали отчёт как артефакт. История сохранялась бы между pipeline-запусками, а секреты перед публикацией маскировались.

## Короткая памятка

- `pytest-html` создаёт простой статический HTML-отчёт.
- `--self-contained-html` делает отчёт переносимым одним файлом.
- Скриншоты в `pytest-html` нужно добавлять явно через extras.
- `allure-pytest` собирает результаты, Allure CLI строит отчёт.
- `allure-results` — сырые данные, `allure-report` — готовый отчёт.
- `allure serve` — быстрый временный просмотр.
- `allure generate` — создание постоянного отчёта.
- `epic`, `feature`, `story` группируют тесты по функциональности.
- Steps показывают логические этапы теста.
- Attachments помогают диагностировать падения.
- Severity означает критичность проверки, а не найденного дефекта.
- История Allure требует сохранения данных между запусками.
- Секреты и персональные данные нельзя публиковать в отчётах.
